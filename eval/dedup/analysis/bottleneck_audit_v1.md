## 2. Precision / recall 损失来自哪里

`.12` 加权 P/R/主决策一致率为 **67.99% / 77.59% / 88.28%**。
因此完整开发集当前是 precision 低于 75% 约 7.01pp；recall 已高于 75% 约 2.59pp。
此前 `.28` 的低 recall 是另一个局部分母，不能混为一个持续下降的总体曲线。

以下“明确语义错误”和“争议”均是本轮预测可见的 AI 开发归因，需由独立评审验证其可靠性。
争议不等于旧标签已被证明错误，也不能从正式计分分母中删除。

| 原因 | 主分歧条数 | 误合并条数 / 权重 | 漏判条数 / 权重 | precision 损失贡献 | recall 损失贡献 |
|---|---:|---:|---:|---:|---:|
| 明确语义错误（开发复核） | 34 | 31 / 304.71 | 1 / 10.05 | 17.84pp | 0.67pp |
| 口径／参照争议 | 56 | 21 / 199.13 | 31 / 284.37 | 11.66pp | 19.00pp |
| 工程问题 | 4 | 0 / 0 | 2 / 17.14 | 0 | 1.15pp |
| 输入受限 | 23 | 0 / 0 | 2 / 2.00 | 0 | 0.13pp |
| 尚未判明 | 7 | 5 / 42.84 | 2 / 21.82 | 2.51pp | 1.46pp |
| 总计 | 124 | 57 / 546.68 | 38 / 335.37 | 32.01pp | 22.41pp |

定义：P 损失贡献 = 该类 FP 权重 / 原 TP+FP；R 损失贡献 = 该类 FN 权重 / 原 TP+FN。
两列分别加总到 `100%-P` 和 `100%-R`，**不是把低于75%的缺口直接分摊，也不是可相加的修复收益**。
5 个仅方向错误中，1 个归明确语义错误、4 个归争议；它们影响主决策一致率，不影响 duplicate P/R。
另外 29 个错误未决按证据分别归类，不能把全部未决一概算作工程错误；正例未决已经计入 FN，不重复加总。

目前可以支持的判断：

- 明确语义错误占原 FP 权重 **55.74%**。实际主体/服务对象、非空商品锚点、部分翻译和保留条件仍有可修问题。
- 争议项占原 FN 权重 **84.79%**。这说明应优先仲裁召回目标中的记录单位/条件保留边界；
  **不说明84.79%的漏判都已证明模型正确**，也不构成改标后 recall。
- 23 个输入受限分歧占主一致率损失 2.12pp，但对 recall 损失只占0.13pp。
  改善可见输入有意义，却不能单独填补当前 precision 缺口。
- 四个工程问题中，两条 exact 被不存在的独有证据要求挡住；另两条是无效 span 引用或缺失冲突证明。
  H0679 的 Payment→page-role 是语义误读，校验挡成未决只是后果，不能靠放松引用要求“修好”。

### 有条件的修复空间，不是新候选成绩

若 TP 完全不损失，只把 FP 纠正为 NO，要达到 P=75% 需减少 FP 权重159.71，
约为本轮明确语义 FP 权重的52.4%。这是数值空间，不保证某条规则能无回退地实现。

机器报告还提供“只让某一原因的所有错误匹配旧参照”的理想化主决策上界：

- 仅全部工程项修正：P/R=68.30%/78.73%，仍不足以过 precision。
- 仅全部明确语义项修正：P/R=82.87%/78.26%。这只是无回退、全修对的假设，不是实测能力。
- 争议项的对应上界仅用于显示对旧参照的敏感性，不能解释为批准改标；所有上界均不得相加或选作版本成绩。

## 3. 参照矛盾不只一个，但不能解释全部差距

按完整原文逐字符比较，显式统一 A/B 替代方向后，发现两组主标签矛盾：

1. H0177 / H0634：完整有序 payload 相同，分别要求 containment 和 no/no。
2. H0053 / H0739：两篇完整原文只是互换 A/B，分别要求 no/no 和 yes/yes。
   一侧额外的禁止上传附件消息不能在相同文本上同时“必须保留”和“完全无差异”。

未使用大小写/空白归一化去制造“相同输入”，也没有把截断后的空 text 当相同文档。
第二组的方向归一化后仍冲突，不是 A/B 方向抄反造成的假冲突。
如果要求同输入给出方向一致的同一答案，这两组带来至少20.09权重的参照不一致，
约占完整主决策分母0.20pp；这两组本身远不足以解释整体缺口。

更大的争议来自政策边界，而不是完全同输入：同一实质 X 加独立 Y 是否 containment、
非正文中哪些具体同意条件必须保留、裸标题/文件名是否绑定身份。
见[仲裁优先级与规则选项](bottleneck_arbitration_v1.md)。

## 4. Critic 的净影响：保留成功，也统计误伤

下表是同一份 `.12` main 原响应，不是重跑另一个 main：

| 完整1,000条处理方式 | 加权 P | 加权 R | 加权主决策一致率 |
|---|---:|---:|---:|
| main-only，保留 v6-route 主路由 | 61.74% | 87.12% | 87.12% |
| main + 原 critic + v6 仲裁 | 67.99% | 77.59% | 88.28% |

v6 的 retained-conflict 合同要求 critic，因此 main-only 显式采用保留同一主语义路由的 v6-route，
而不是把缺失 critic 伪装成符合 v6 的响应。此消融测量的是 critic **连同其仲裁职责**，不独立证明某个模块的语义能力。

- 修正24条主决策，权重250.94；全部是原误合并变正确分离。
- 弄错13条，权重134.04：11条变漏判、2条 exact 变未决。
- 加权主决策净增1.17pp；还存在1条“原方向错→漏判”及1条“误合并→未决”，不能漏报这些仍错的变化。
- duplicate TP 权重减少142.61，FP权重减少260.99；加权 P +6.24pp、R −9.53pp。
- 11条正确→已决漏判均落在本轮待确认的记录/页面边界；这是仲裁优先级证据，不是已批准的免责。

因此目前不支持全局关闭 critic，也不支持用“它否决了多少条”充当收益。
应把明确纠错能力、无根据否决、协议导致的未决分开验证。
