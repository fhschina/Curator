# .33-exp1 限流等待续跑

在原同轮恢复上追加传输层规则，不改任何冻结的 Judge、critic、schema、模型请求、
输入、参考、评分或旧文件。75 条既有结果（含 H0074、H0075 工程失败）及请求/响应
全部冻结保留。新的说明文件明确这是传输策略变更，不宣称调度与最初完全相同。

暂时性 HTTP 429 不进入主 Judge 的语义纠错循环，不生成终态失败占位符。
保存脱敏后的提供方 error message/type/code 和白名单限流头；禁止保存认证头、key、
任意响应头或完整非 JSON 错误页。每次 HTTP 尝试仍加入原 transport_events，
同一请求的限流等待及再次发送额外记在本会话 collection_events。

收到 429 后等待至少 Retry-After；本地退避从 60 秒递增至 300 秒，不缩短提供方
要求的更长等待。相同请求体原样重发，成功响应只保存一次，不从多个成功回答中择优。
每个阶段最多 60 次限流尝试，等待窗口最多 6 小时；超过预算保留待完成状态并停止，
不把基础设施不可用算作语义错误。全轮 24,000 次外部尝试预算不增加。

仍然双并发、2 秒发送间隔，600 秒单次超时；其他 5xx/网络错误沿用最多两次传输
尝试，鉴权错误等非重试错误仍停止。已有失败结果不回填成成功，完整评分仍使用原
export，另附 rate_limit_final.json 说明 429 和额外等待/重发，旧 transport_retries
字段只含原 relay 内重试，不冒充所有恢复重发的总数。

不单独刷小请求试探限额，使用剩余正式样本收集下一次限流说明。GET /models 的
一次元数据检查只验证旧 key 可用，不当成推理配额或服务容量正常的证据。
用户授权慢速继续，不扩大并发、不更换 key/模型、不改语义、不重跑已完成样本。
